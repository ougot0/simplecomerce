================================================================================
1. LE BUT DU PROJET
================================================================================

Simple Commerce est un portail web (https://simplecommercess.com) qui permet à
des commerçants et artisans NON TECHNIQUES de modifier eux-mêmes le contenu de
LEUR PROPRE SITE, là où il est hébergé, sans le reconstruire ailleurs :
produits, prix, stocks, photos, textes, horaires, projets, tarifs,
ouverture / fermeture de la boutique.

Un seul portail, plusieurs sites. Chaque client ne voit que les siens. Un
administrateur voit tout, peut « agir pour » un client et consulte un journal.

Objectif à terme, exprimé par le propriétaire : que N'IMPORTE QUEL site soit
modifiable « comme Shopify », quelle que soit la façon dont il a été construit,
sans préparation et sans développeur. Les clients ne sont pas forcément chez
OVH : le portail doit relier des sites hébergés n'importe où.

Contraintes de départ qui expliquent la plupart des choix techniques :
- Le portail tourne sur un hébergement OVH MUTUALISÉ : PHP + MySQL seulement,
  pas de Node.js, pas de terminal garanti, pas de Composer.
- Le propriétaire n'est pas développeur : l'installation se fait par FTP, sans
  aucune étape technique (le portail s'installe seul).
- Les utilisateurs finaux ne sont pas techniques : aucun jargon dans l'interface.

3. LANCER LE PROJET EN LOCAL
================================================================================

Démonstration (2 faux sites, 3 comptes, base SQLite) :

    cd portail
    SC_DEMO=1 SC_ALLOW_PRIVATE=1 php -S 127.0.0.1:8080 -t public public/index.php

    http://127.0.0.1:8080
    Comptes de démo :
      marie@patisserie-lune.fr   / tarte-citron-2026   (cliente)
      paul@atelier-brun.fr       / maison-bois-2026    (client)
      alex@simplecommerce.demo   / atelier-demo-2026   (administrateur)

    Effacer portail/storage/ remet la démo à zéro.

Sans SC_DEMO, le premier passage installe le portail tout seul (voir 9).
Lancer aussi avec SC_URL=http://127.0.0.1:8080 : sinon les scripts publics
(catalogue, avis, rendez-vous…) appellent la mauvaise adresse.

Variables pour tester contre des imitations des services extérieurs :
    SC_STRIPE_API      adresse de remplacement de l'API Stripe
    SC_BREVO_API       adresse de remplacement de l'API Brevo
    SC_ANTHROPIC_API   adresse de remplacement de l'API Claude

Tests :

5. LE PARCOURS D'UNE REQUÊTE
================================================================================

1. public/index.php charge src/bootstrap.php puis App::handle().
2. App installe le portail si config.php n'existe pas encore, passe en https
   si possible, applique les en-têtes de sécurité (CSP stricte), vérifie le
   jeton CSRF sur tout POST, puis trouve la route.
3. Les routes d'un site sont sous /s/{slug}/… Le contrôleur appelle
   Access::site($slug) : si l'utilisateur n'est pas membre, réponse 404.
4. Pour lire ou écrire le contenu, le contrôleur passe par Services\Sites
   (qui ouvre le connecteur avec les accès déchiffrés) et Services\Changes
   (qui écrit, garde l'avant / après pour l'annulation et notifie).
5. La page est rendue par View::render(gabarit, variables, mise en page).

6. LE MOTEUR DE CONTENU
================================================================================

Notion centrale : la RUBRIQUE (« section »). Un site est décrit par un
« schéma » = une liste de rubriques, stocké en base (table sc_schemas,
versionné). Chaque rubrique a :
  - key, label            identifiant et nom affiché
  - kind                  « collection » (liste d'éléments : produits, projets…)
                          ou « singleton » (un seul bloc : textes d'une page,
                          horaires, ouverture…)
  - fields                les champs : text, textarea, richtext, price, number,
                          boolean, select, image, gallery, url, date…
  - titleField, imageField, idField…   pour l'affichage des listes
  - source                où se trouve le contenu : fichier + chemin dans le
                          fichier + format (json, yaml, markdown, js, jsvars,
                          html), ou dossier (un fichier par élément)

D'où vient le schéma ?
  a) Le site fournit un fichier simplecommerce.json : il est utilisé tel quel.
  b) Sinon DÉTECTION AUTOMATIQUE (Content\Infer) sur les fichiers de contenu.
  c) Site fait main, sans fichier de contenu : FileSiteAdapter parcourt les
     .js, .json et .html du site (findProductFiles) et garde :
       - les listes de produits écrites en JavaScript (JsLiteral)
       - les fiches répétées des pages HTML (HtmlCards::find) : blocs frères
         de même classe avec un titre h1-h6 et un prix, un texte ou une photo
         (photo en <img> ou en background-image), étiquette, liste à puces
       - les textes de chaque page (HtmlCards::texts) : titres, paragraphes,
         légendes, photos, hors menu, liens, boutons, formulaires et fiches
       - un réglage ouvert / fermé (booléen nommé open / ouvert / ferme…)
       - le logo du site (HtmlCards::logo) : rubrique « Logo du site » de
         source {type: logo}, remplacé dans toutes les pages par
         FileSiteAdapter::writeLogo (logo, texte à côté, icône de l'onglet)
     Les pages qu'aucune autre page ne relie (projet supprimé) sont écartées.
  L'administrateur peut ensuite renommer ou masquer des rubriques.

Écriture CONSERVATRICE (règle absolue) :
  - On ne réécrit JAMAIS tout un fichier du client. Formats::parse garde le
    texte d'origine et son style (indentation, guillemets, virgules finales,
    ordre, champs inconnus) ; Formats::serialize ne remplace que les éléments
    modifiés. En HTML, seuls le texte, la photo ou la liste concernés changent.
  - Conflit optimiste : le formulaire garde l'empreinte du contenu affiché ;
    si le site a changé entre-temps, l'écriture est refusée.
  - Écriture atomique (fichier temporaire puis renommage), chmod 0644.
  - Les photos sont envoyées dans la MÊME écriture que le contenu : la valeur
    « sc-media:<uuid> » est remplacée par le chemin final sur le site.

Prix (Content\Price) : réécrits dans le format du site (nombre, centimes ou
texte « 4,50 € »). Un prix rond reste rond (« 49 € »).

Ajout d'une fiche HTML : copie de la dernière fiche ; les liens de paiement
Stripe / PayPal de la copie sont remplacés par « # ». Si les fiches mènent à
leur propre page (projet-x.html), la page du nouvel élément est créée en
copiant celle de la fiche d'origine (FileSiteAdapter::addDetailPage,
HtmlCards::copyPage). Supprimer garde le fichier de page (rien n'est perdu).
Après un ajout ou une suppression dans une page HTML, le schéma est relu
(Sites::rediscover).

7. LES CONNECTEURS
================================================================================

Interface commune (Adapters\Adapter) :
  test, discover, listEntries, getEntry, createEntry, updateEntry,
  deleteEntry, reorder, getSingleton, updateSingleton, template,
  getStatus, setStatus, capabilities, close

Connecteurs (choisis par Adapters\Registry selon sc_sites.connector) :
  sftp, ftp      Fichiers chez n'importe quel hébergeur. Préréglages par
                 hébergeur (OVH, o2switch, Hostinger, IONOS, Infomaniak, LWS,
                 PlanetHoster). SFTP : empreinte du serveur mémorisée puis
                 vérifiée. FTP : mode passif, liste via LIST si MLSD manque.
  github, gitlab, bitbucket   Fichiers dans un dépôt de code (chaque
                 modification = un enregistrement signé « via Simple Commerce »)
  netlify        Site déposé sur Netlify sans dépôt de code (NetlifyBackend) :
                 jeton personnel ; lecture par l'API des fichiers ; chaque
                 modification = nouveau déploiement par empreintes SHA1 (seuls
                 les fichiers changés sont envoyés). Refusé si le site se
                 reconstruit depuis un dépôt ou utilise des fonctions Netlify.
                 Testé seulement contre une imitation de l'API.
  shopify        API Admin GraphQL 2026-07, Client ID + Client secret
                 (jeton de 24 h obtenu à chaque connexion)
  wordpress      API REST WordPress + WooCommerce (mot de passe d'application)
  webflow        API Webflow (collections du CMS)
  custom-api     Interface sur mesure pour les sites avec base de données
                 (contrat : docs/API-SUR-MESURE.md, exemple :
                 examples/simplecommerce-endpoint.php)
  catalogue      Catalogue hébergé dans la base du portail (table sc_files,
                 DbBackend) + ligne à coller sur le site du client :
                 <script src="https://…/catalogue/{clé}.js"></script>
                 Le widget (public/assets/catalogue-widget.js) s'affiche dans
                 un Shadow DOM pour ne pas casser le style du site.
  demo           Dossier local (démonstration uniquement)

FileSiteAdapter : un seul adaptateur pour tous les connecteurs « fichiers »,
au-dessus d'un FileBackend (read, list, commit, test, close).

Fermeture temporaire : fichier simplecommerce-statut.json
{ferme, message, reouverture} dans le dossier de contenu ; GET / PUT /status
pour l'interface sur mesure ; pour Shopify, WordPress et Webflow, le portail
explique où cliquer dans leur administration.

7 bis. FONCTIONS AJOUTÉES EN VERSION G (13 octobre 2026)
================================================================================

Rendez-vous (Services\Bookings) : réglages dans sc_sites.config['extras']
['booking'] (prestations {nom, duree, prix}, créneaux par jour de la semaine
ou horaires d'ouverture, délai minimum, horizon, capacité). Créneaux libres
calculés à la demande (pas fixe 5 / 10 / 15 min), congés respectés, heure de
Paris. Réservation revérifiée sous verrou (storage/rdv-<site>.lock), 5
rendez-vous à venir au plus par e-mail. Widget public/assets/rdv-widget.js
(Shadow DOM, 4 étapes).

« Écrire pour moi » (Services\Writer) : bibliothèque officielle
anthropic-ai/sdk, modèle claude-opus-5-5, effort « low », repli automatique
côté serveur (fallbacks « default »). Boutons ajoutés par sc_ai() dans
templates/site/fields.php sous les champs textarea, markdown et richtext ;
le navigateur envoie les autres champs de la fiche (nom, prix…) à
/s/{slug}/ecrire. Le texte proposé remplace le champ ; « Revenir au texte
d'avant » annule.

Version anglaise (Services\Translation + Content\HtmlTranslate) : pour les
sites reliés par fichiers. Étapes : preparer (relevé des textes de toutes les
pages, liste de ce qui n'est pas encore traduit), etape (un paquet de 80
textes / 5 000 caractères au plus par appel, traduit par Claude en sortie
structurée JSON), publier (écriture de x-en.html à côté de x.html + bouton
de langue, en une seule écriture). Mémoire de traduction :
storage/traductions/<site>-memoire.json. Les pages -en.html sont exclues de
la détection du contenu (SKIP_SCAN dans FileSiteAdapter).

Autres : bon de commande / facture (ShopController::orderDocument, gabarit
site/order-document.php, mise en page « bare » imprimable) ; aperçu
téléphone (SiteController::phone) ; résumé du lundi et rappel de fin de
période gratuite (Services\Digest, appelés par le Scheduler) ; parrainage
(Services\Referral, crédit Stripe au 1er paiement du filleul, avis
invoice.paid) ; revenus (Billing::revenue, lu chez Stripe) ; Brevo
(Support\Mailer) ; vérification de l'adresse e-mail
(Auth::sendVerification, SitesController::verifiedOrPage).

Tout cela n'a été testé que contre des imitations de Claude, Stripe et
Brevo : à vérifier avec les vrais services.

Petites données dans sc_meta (clé → valeur) : réglages Stripe, Brevo et Claude
(clés chiffrées), informations légales, « unverified:<id> » (adresse non
vérifiée), parrainage (refcode:, referredBy:, refPending:…), numéros de
facture (invoiceSeq:<site>:<année>), rappels déjà envoyés.

Version du schéma : Schema::VERSION (5). Schema::migrate() est appelé à chaque
requête et par cron.php : si la base est plus ancienne, les tables manquantes
sont créées (CREATE IF NOT EXISTS), les migrations ponctuelles passent (v4 :
période gratuite 7 → 365 jours) et les catalogues reçoivent les nouveaux
champs (DbBackend::upgradeSchema). Réglages par site (seuil de stock,
horaires, fermeture prévue, commandes, avis, statistiques…) : dans
sc_sites.config['extras'] (Sites::extras / setExtras). Clé publique d'un site
(24 caractères hexadécimaux) : config['publicKey'] (Sites::publicKey).

NE JAMAIS renommer une table ou une colonne sans migration : des bases sont
déjà en service.

9. INSTALLATION ET MISE EN LIGNE (OVH MUTUALISÉ)
================================================================================

Installation automatique (InstallController::autoInstall) : au premier
passage, si config.php n'existe pas, le portail crée une base SQLite
(storage/simplecommerce.sqlite, sans mode WAL à cause des disques réseau),
génère ses clés, écrit config.php et ouvre les inscriptions.
LE PREMIER COMPTE CRÉÉ DEVIENT ADMINISTRATEUR. MySQL reste possible en secours.

Où sont les données (depuis la version E) : config.php et storage/ (base
SQLite, sessions, photos, sauvegardes, mémoire de traduction) sont dans le
dossier VOISIN du portail : SC_DATA = dirname(SC_ROOT)/simplecommerce-donnees
(sc_data_dir() dans bootstrap.php ; déménagement automatique la 1re fois).

10. SÉCURITÉ — RÈGLES NON NÉGOCIABLES
================================================================================

- Accès des sites chiffrés (Vault : sodium XChaCha20-Poly1305, préfixe « v1: »,
  l'identifiant du site sert de donnée associée). Jamais renvoyés au
  navigateur (seule une empreinte « …a3F9 » est affichée), jamais dans les
  journaux (Log::redact), jamais dans le code ni le dépôt.
  Ne pas changer ce format sans migration.
- Isolation : chaque page et action passe par Access::site() /
  Access::section(). Site non autorisé = 404 (et non 403).
- Appels sortants uniquement côté serveur, sans suivre les redirections,
  https obligatoire, adresses privées refusées (Net::assertPublicHost/Url).
  Exceptions : SC_ALLOW_PRIVATE=1 en démo, ou 'allow_private_hosts' => true
  dans config.php (tests, désactivé par défaut).
- Photos : vrai type vérifié (finfo + getimagesize), pas de SVG, poids et
  pixels limités, réencodées en WebP, EXIF / GPS retirés, 8 Mo maximum.
- CSRF sur tous les POST (aussi en en-tête X-CSRF-Token). Cookies HttpOnly,
  SameSite=Lax, Secure en https. CSP stricte : script-src 'self', aucun
  script ni style en ligne, aucun domaine tiers.
- Connexion : 8 tentatives / 15 min par e-mail, 30 par adresse IP.
- « Rester connecté » : jeton haché en base, 400 jours, renouvelé à chaque
  visite (donc sans limite tant que la personne revient).
- Texte enrichi nettoyé par liste blanche (p, br, strong, em, a, ul, ol, li).
- Seule la page d'accueil publique est indexable ; tout le reste est
  « noindex » et interdit dans robots.txt.
- Adresses publiques appelées par les sites des clients (PublicController) :
  sans session ni cookie, corps en texte (pas de pré-requête CORS), limitées
  par IP (l'IP n'est gardée que hachée), champ piège « site_web » contre les
  robots. Prix et stock d'une commande toujours relus côté serveur.
- Statistiques : aucun cookie, aucune IP, seulement des compteurs par jour ;
  sessionStorage sert uniquement à savoir si c'est la 1re page de la visite.
- Abonnements : clé Stripe et secret du webhook chiffrés (Vault, donnée
  associée « simplecommerce-billing »), avis Stripe vérifiés par signature
  HMAC (5 min de tolérance). Le portail ne voit jamais de carte bancaire.
  Codes promo : 8 caractères minimum, 10 utilisations au plus.
- Clés Brevo et Claude chiffrées (données associées « simplecommerce-mail »
  et « simplecommerce-ia »), jamais renvoyées au navigateur ; Log::redact
  masque sk_, rk_, whsec_, nfp_, sk-ant-…
- Comptes : adresse e-mail vérifiée avant de relier un site ; changement de
  mot de passe = ancien mot de passe demandé + autres appareils déconnectés.
- Anti-SSRF renforcé : IPv6 contenant une IPv4 privée refusée, IP vérifiée
  imposée à cURL (CURLOPT_RESOLVE) et aux connexions FTP / SFTP.
- Rédaction automatique : 40 demandes par personne et par jour, traduction
  20 fois par site et par jour ; rien n'est publié sans action du client.
- Version anglaise : seules les pages « -en.html » portant la signature du
  portail (meta generator) sont remplacées ou supprimées ; les pages
  françaises ne reçoivent qu'un bloc balisé (<!-- simplecommerce-langue -->)
  retiré sans trace.

11. CE QU'IL NE FAUT SURTOUT PAS FAIRE
================================================================================

- Commiter config.php, storage/ ou de vrais identifiants.
- Exposer autre chose que public/ sur Internet.
- Ajouter Node.js, une étape de « build », un CDN ou Google Fonts.
- Mettre « php_value » dans un .htaccess (erreur 500 sur OVH mutualisé).
- Supprimer vendor/ ou le rendre incompatible avec PHP 8.1.
- Réécrire tout un fichier de contenu d'un client.
- Affaiblir l'isolation, le CSRF, l'anti-SSRF, la validation des photos ou
  le masquage des secrets.
- Bloquer les actions automatiques quand un abonnement est fini : les
  commandes des clients et les fermetures programmées passent toujours
  (Billing::$system).
- Supprimer la version Next.js sans l'accord du propriétaire.
- Supprimer ou écraser le dossier simplecommerce-donnees/.
- Mettre « RewriteCond %{ENV:REDIRECT_STATUS} » dans un .htaccess (chez OVH
  toutes les pages passent en erreur 500).
- Écrire « Kumao » ou « Coumao » dans le portail (site d'exemple sans
  rapport avec Simple Commerce).

12. INTERFACE ET TON
================================================================================

- Couleurs : fond #f4efe6, cartes #ffffff, beiges #ebe3d5 / #d9ccb6, lignes
  #e4dccf, encre #141210, textes #4b453e / #8b8377. Menu latéral noir, boutons
  principaux noirs en pilule. Rouge sombre #a12d1f réservé aux erreurs et
  suppressions. Variables CSS en tête de public/assets/app.css.
- Police Figtree (400 à 700), servie localement.
- Icônes SVG au trait (icon() dans helpers.php), jamais d'emoji.
- À éviter : dégradés violets, polices Inter / Geist / Space Grotesk, petit
  label en majuscules au-dessus d'un grand titre centré, animations inutiles,
  faux témoignages.
- Ton : français simple, vouvoiement, phrases courtes. Jamais de jargon pour
  un client (« JSON », « API », « commit », « token », « dépôt »…). Les
  boutons disent ce qu'ils font : « Publier sur mon site », « Enregistrer sans
  publier », « Relier mon site », « Tester la connexion ». Accords gérés par
  Text::plural et Text::addLabel.
- Le JavaScript est une amélioration : les formulaires marchent sans lui
  (champs « data[clé][ligne][sous-clé] » reconstruits par FormInput::coerce),
  sauf pour l'envoi de photos, l'ajout ou le déplacement de lignes, le texte
  enrichi et le test de connexion sans recharger.

13. AJOUTER UN NOUVEAU CONNECTEUR (exemple de démarche)
================================================================================

1. Créer src/Adapters/MonAdapter.php qui implémente Adapter (s'inspirer de
   WebflowAdapter ou WordPressAdapter), ou un nouveau FileBackend si le site
   est un ensemble de fichiers.
2. L'enregistrer dans Adapters\Registry (création + validation de la config).
3. Ajouter le choix et son formulaire dans l'assistant « Relier un site »
   (SitesController + templates/sites/).
4. Les secrets passent UNIQUEMENT par Sites::storeSecrets (chiffrés).
5. Tout appel sortant passe par Support\Http (anti-SSRF inclus).
6. Ajouter des vérifications dans tests/run.php, puis tester contre un vrai
   compte ou une imitation fidèle de l'API.
